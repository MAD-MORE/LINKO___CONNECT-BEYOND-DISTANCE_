# Architecture Decision Records — Linko

## ADR-001: Android-First MVP

**Status:** Accepted  
**Date:** 2026-08

**Context:** Linko's core value proposition (connectivity sharing via VPN APIs) requires deep OS-level network control. Android provides `VpnService` which allows an app to capture and route device traffic without root. iOS has significant restrictions on background VPN establishment and does not permit the equivalent Provider-side traffic forwarding without MDM profiles.

**Decision:** Build the MVP exclusively for Android.

**Consequences:** iOS users cannot use Linko in the MVP. This is acceptable for the initial market validation phase.

---

## ADR-002: Supabase for Authentication and Realtime

**Status:** Accepted  
**Date:** 2026-08

**Context:** Building a production-grade auth system (email verification, password reset, OTP, token refresh) from scratch is high-risk and time-consuming. Supabase provides all of this plus a Realtime WebSocket layer for live presence.

**Decision:** Use Supabase for user authentication, OTP flows, friend relationship storage, and Realtime presence. The Linko backend uses Supabase JWT verification for device registration; subsequent API calls use Linko-issued device JWTs.

**Consequences:** Supabase is a managed dependency. Outages affect signup and new device registration but not existing active sessions. Migrating away from Supabase later would require custom auth implementation.

---

## ADR-003: Custom Control Plane (Node.js / TypeScript)

**Status:** Accepted  
**Date:** 2026-08

**Context:** Supabase alone cannot enforce Linko's session authorization model (Provider must explicitly approve; friendship must be verified; tunnel keys must be issued server-side). A custom control plane is required.

**Decision:** Build a lightweight Node.js/TypeScript HTTP server (`backend/`) as the Linko control plane. It handles device registration, session lifecycle, signaling brokering, tunnel key management, usage accounting, and admin operations.

**Consequences:** We own and maintain the control plane. It must be deployed, monitored, and scaled independently.

---

## ADR-004: Polling-Based Signaling (Not WebSocket)

**Status:** Accepted  
**Date:** 2026-08

**Context:** A WebSocket-based signaling server is more efficient but adds significant complexity to both the backend (connection management, reconnect handling) and Android (lifecycle management of persistent WebSocket).

**Decision:** Use HTTP polling for signaling (offer/answer/ICE exchange). Android polls `GET /v1/sessions/:id/signaling` every 2 seconds while in `SIGNALING` state. Messages are queued server-side and drained on each poll.

**Consequences:** Signaling latency is up to 2 seconds per round-trip. For an MVP this is acceptable — it adds 2–6 seconds to session establishment. Supabase Realtime is used for presence (online/offline), which is lower-frequency.

**Future:** Upgrade to WebSocket signaling post-MVP if session establishment latency becomes a user complaint.

## ADR-005: UDP Relay with AES-GCM Encryption

**Status:** Accepted  
**Date:** 2026-08

**Context:** The data plane requires a transport that: (a) is encrypted end-to-end, (b) works across NAT, (c) is relay-able without the relay reading plaintext, (d) is implementable in Kotlin on Android.

**Decision:** Use UDP datagrams encrypted with AES-256-GCM. Session keys are 32-byte random values issued by the control plane. The relay node forwards ciphertext without decryption. The `EncryptedDatagramTunnel.kt` implements this on Android.

**Consequences:** No forward secrecy (session key is static for session lifetime). Acceptable for MVP. Post-MVP: evaluate WireGuard or DTLS for forward secrecy.

## ADR-006: Direct Path First, Relay as Fallback

**Status:** Accepted  
**Date:** 2026-08

**Context:** Relay bandwidth is the primary infrastructure cost driver. Direct UDP paths (via STUN hole-punching) have zero relay bandwidth cost.

**Decision:** Always attempt direct UDP path first using ICE/STUN. Fall back to relay only when direct connectivity cannot be established within 10 seconds. The `LinkoStateMachine` manages this fallback.

**Consequences:** Session establishment is slower in relay-fallback cases (up to 10 seconds extra). Cost savings outweigh this for MVP.

## ADR-007: Fly.io for Hosting

**Status:** Accepted  
**Date:** 2026-08

**Context:** Relay nodes require UDP port exposure, which many PaaS providers don't support. Fly.io supports anycast UDP, has a simple CLI, supports Docker containers, and has a reasonable free tier. It also supports multi-region deployment needed for relay latency.

**Decision:** Deploy backend, relay, and PostgreSQL to Fly.io.

**Consequences:** Fly.io is a single-vendor dependency. If Fly.io has an outage, Linko is down. Mitigation: backend is stateless and can be redeployed to another provider; PostgreSQL can be migrated via pg_dump.

---

## ADR-008: PostgreSQL as the Control Plane Database

**Status:** Accepted  
**Date:** 2026-08

**Context:** Session state, device registry, usage records, and security events require ACID guarantees and relational integrity (foreign keys, constraints). NoSQL databases introduce eventual consistency risks for authorization checks.

**Decision:** Use PostgreSQL for all control plane state.

**Consequences:** Requires migration management (sequential SQL migration files). Schema changes require migration + deploy coordination.

---

## ADR-009: Provider Consent is Server-Side Enforced

**Status:** Accepted  
**Date:** 2026-08

**Context:** Provider consent is the most critical security invariant in Linko. If the client could bypass consent enforcement, a malicious Receiver could use a Provider's connection without approval.

**Decision:** The `approved` session state transition can ONLY be performed by a request authenticated as the Provider's device. This check is enforced in `server.ts` and cannot be overridden by the Android client. There is no API endpoint that allows Receiver to self-approve.

**Consequences:** Provider must be online and actively approve. This is by design. Offline approval (e.g. pre-authorized auto-approve) is a post-MVP feature that will require a separate security review.

---

## ADR-010: Separate Device Identity from User Identity

**Status:** Accepted  
**Date:** 2026-08

**Context:** A user may use Linko on multiple Android devices. Sessions are negotiated between specific devices (not just users), which matters for tunnel key routing and relay assignment.

**Decision:** Linko maintains two layers of identity:
- **User identity** (Supabase user ID): used for friendships, account-level operations
- **Device identity** (Linko device ID + JWT): used for session creation, tunnel routing, presence

`LinkoDeviceIdentity.kt` generates a permanent device ID persisted in EncryptedSharedPreferences. Friend relationships are user-to-user. Session authorization checks both the user-level friendship AND the device-level registration.

**Consequences:** Device revocation is supported (mark device as `revokedAt`). A user can see their registered devices and revoke compromised ones.
